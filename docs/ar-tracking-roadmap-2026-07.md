# 実写AR トラッキング強化ロードマップ (2026-07)

「指トラッキングに固定せず、人体推定・姿勢推定エンジンとしてどこまで行けるか」の整理。
結論: **姿勢推定エンジンは既に本体に組み込み済み**。以降は「どの構成に張り替える/積み増すか」の段階。

## 0. 現在の構成(実装済み)

| 層 | 実装 | 役割 |
|---|---|---|
| 姿勢推定 | **MediaPipe PoseLandmarker (BlazePose GHUM / full)** GPU delegate | 33関節の3D座標(画面+world/メートル)。骨格表示・IK・奥行き配置・体の向き全ての土台 |
| 人物マスク | 同モデルの segmentation 出力 | 背景置換(存在の消去)用 |
| 手指 | **HandLandmarker**(21点×2手、dev限定) | 指カール駆動。左右はポーズ手首との画面距離で対応付け |
| 平滑化 | One Euro Filter(world用+2Dアンカー用の2バンク) | ジッタ抑制と追従性の両立 |
| リギング | 自作: 到達球つきTwo-Bone IK(腕/脚)、ルートyaw(baseYaw基準)、奥行き配置 | エンジン出力→VRMボーン |
| VR(参考) | Quest WebXR Body Tracking API + 手続き式フォールバック | /ar の別系統 |

計測手段: `/mirror/<code>?dev=1` のAR計測パネル(骨格/残差px/fps/距離/yaw)。

## 1. 上げ幅の候補(コスト順)

### ① Poseモデル full → heavy 差し替え 【コスト極小】
- モデルURLの1行変更。精度↑・fps↓(60→30台の可能性)
- やり方: dev パネルにモデル切替トグルを足し、残差pxとfpsでA/B実測
- 判断基準: heavy で残差が明確に下がり、fps>24 を維持できるなら常用

### ② ImageSegmenter(専用セグメンテーション)追加 【コスト小・効果大】
- 現マスクはポーズ推定の副産物で輪郭が粗い。専用モデル(selfie multiclass 等)は
  髪・体・服を分類でき、**「存在を消す」品質が一段上がる**
- 実機指摘「輪郭品質まだまだ」への最有力打ち手
- 併用コスト: 3モデル同時推論になるためfps実測必須(頻度を1/2フレームに落とす等の調整枠あり)

### ③ HolisticLandmarker(ポーズ+手+顔の統合単一パス) 【要調査】
- 整合性は理想的だが、JS(tasks-vision)での提供が不安定。
  顔不要(スーツで隠れる)方針なら現行「Pose+Hands二本立て」が実質同等
- tasks-vision のリリースノートを定期確認、安定提供されたら乗り換え検討

### ④ サーバ側3D人体メッシュ復元(SMPL系: HybrIK / 4D Humans 等) 【コスト大・別枠】
- リアルタイム不可だが、将来像「スマホで撮って変身動画を残す」に最適:
  撮影動画→鍛造炉(Cloud Run)→オフラインで高精度復元→変身動画をレンダして返す
- リアルタイム鏡とは別の「品質最優先・非同期」ルートとして設計する
- 前提: GPU付きジョブ(Cloud Run GPU or バッチ)、処理数分/本の世界

### ⑤ リギング層の強化(エンジン非依存) 【継続投資】
- 背骨の多節化(spine/chest/upperChest配分)、足接地ロック、
  モデルシルエットを実写輪郭に合わせる「輪郭フィット」(細い部位のはみ出し対策)
- エンジンを変えずに体感が上がる領域。残差の残りはここが支配的の可能性

### 候補外
- TensorFlow.js MoveNet 等: 17点2D・指なし・奥行きなし。現行からダウングレード
- 現行「BlazePose full + Hands + セグメンテーション」は、サーバGPUなしの
  ブラウザ実時間としてほぼ最上位構成

## 2. 推奨順序

1. **実機検証の完了が先**(正対/鏡像の腕対応/背景消去 — HANDOVER T12⑪)
2. ② ImageSegmenter(消去品質 = 直近の最大不満点)
3. ① heavyトグル(A/B実測、採否判断)
4. ⑤ 輪郭フィット・足接地(体感仕上げ)
5. ④ オフライン高品質パイプライン(スマホ・録画ユースの設計と同時に)
6. ③ Holistic は提供状況ウォッチのみ
